## Three search tools, and it picks the wrong one 6 times in 10

Your support agent has three tools: `search`, `search_docs` and `search_tickets`. A user asks "How do I export a report to CSV?" and the agent calls `search`, which queries the public web and returns ten blog posts about other products. Across a day of traffic, about 6 in 10 of its tool calls hit the wrong tool.

<Trace caption="Every tool works, but the model picked web search for a help center question." steps={[

  { role: "model", text: "I couldn't find export steps. Maybe try right-clicking?", tag: "end_turn", bad: true },

Nothing is broken. Every tool works. The model just keeps choosing the wrong one, and about a third of the time it then answers from the wrong results: "I couldn't find export steps. Maybe try right-clicking?"

## The model only sees the label on the box

Here is everything the model knows about those tools:

```text
search          "Search for things."
search_docs     "Search the docs."
search_tickets  "Search tickets."
```

It never sees your code, your database or the help center. It sees a name and one short line, and the three lines say almost the same thing. "Search for things" covers export questions. So does "Search the docs". With no reason to prefer one, the model leans on word overlap with the question, and that is close to a guess.

A tool definition is part of the prompt. You would never give a new support hire three buttons labelled "Search", "Search 2" and "Search 3" and expect them to pick correctly on day one. The model is that new hire, on every single call.

## Write each tool like a note to a new hire

A good description answers four questions, in this order:

1. **What does it do, and to what?** Start with a verb: "Finds help center articles by keyword and returns titles with short excerpts."
2. **When should I use it?** "Use this for how-to questions about features, settings or billing."
3. **When should I not?** "Do not use for questions about a specific customer."
4. **How is it different from its neighbours?** Use words the other tools don't. If two descriptions share most of their vocabulary, the model can't separate them.

```json
{ "name": "search_docs",
  "description": "Finds help center articles by keyword and returns titles with short excerpts. Use this for how-to questions about features, settings, billing or exports. Do not use for customer cases.",
  "input_schema": { "type": "object",
    "properties": { "query": { "type": "string", "description": "2 to 6 keywords, e.g. 'export report csv'" } },
    "required": ["query"] } }
```

The same care goes into the rest of the definition:

- **Names.** Group related tools with a shared prefix (`docs_search`, `tickets_search`) so they read as different things, not variants of one thing.
- **Parameters.** Give each one a description and an example. `customer_id` beats `id`. An `enum` beats a free string.
- **Outputs.** Return what the model needs for the next step, in plain words. A customer's name is more useful than an internal UUID.
- **Errors.** An error message is read the same way. That is [Tool Errors and Recovery](/c/tool_errors/).

## Let us check the math

Take 1,000 questions a day. Each wrong pick costs one extra turn of about 3,000 input tokens before the model tries again, and a third of wrong picks end in a wrong answer.

<Callout type="math" label="Let us check the math">
**Vague descriptions**, 60% wrong first picks: 1,000 × 0.6 = **600 wrong picks**.<br />
Extra input: 600 × 3,000 = 1.8M tokens. At medium sim prices ($3 per million input, illustrative): **$5.40 a day**.<br />
Wrong answers: 600 ÷ 3 = **200 a day**, or 20% of users.<br />
**Clear descriptions** grow each tool from about 5 tokens to about 40: +35 × 3 tools = 105 tokens per call. At 2 calls per question: 105 × 2 × 1,000 = 210k tokens = **$0.63 a day**.<br />
If wrong picks drop to 5%: 50 extra turns ($0.45) and about 17 wrong answers. You spend $0.63 to save $4.95 and about 183 wrong answers.
</Callout>

<Bars caption="Clear descriptions cut wrong answers from 200 a day to about 17." bars={[

  { label: "Clear, 5% wrong picks", value: 17, kind: "good", note: "about 17 a day" },

The tokens are cheap. The wrong answers are what you are really paying for.

## The tradeoff: every word rides on every call

Good descriptions cost a little each, and the bill grows with the size of your toolbox:

- **Tokens per call.** 50 tools at 150 tokens each is 7,500 tokens on every turn. Cache the stable prefix ([Prompt Caching](/c/caching/)) and send only the tools a task needs ([Routing](/c/routing/)).
- **More tools, more overlap.** Each new tool is another look-alike to confuse. Merge small steps into one tool that does a whole job: one `schedule_meeting` instead of `list_users`, `list_events` and `create_event`.

<Compare caption="One tool that does the whole job leaves fewer look-alikes to confuse." cols={[

- **You can't eyeball accuracy.** A description that reads well can still lose. Measure which tool was called on a fixed set of questions ([Trajectory and Tool-Use Evals](/c/trajectory_evals/)).

## In the real world

When Anthropic built its agent for SWE-bench, a benchmark of real GitHub issues, it reported spending more time on the tools than on the overall prompt. One fix: the model made mistakes with relative file paths after changing directory, so the tool was changed to require absolute paths, and the mistakes stopped. Its later guide on writing tools for agents recommends the same habits as this lesson: clear names with namespaces, descriptions written like docs for a new teammate, and checking accuracy with evals rather than by feel.

```json
{ "name": "edit_file",
  "description": "Edits one file. Requires an absolute path.",
  "input_schema": { "type": "object",
    "properties": { "path": { "type": "string",
      "description": "Absolute path, e.g. '/repo/src/app.py'. Relative paths are rejected." } },
    "required": ["path"] } }
```
