## Three apps, four services, twelve integrations

Your team uses three AI apps: your own agent harness, Claude Code and a desktop assistant. You want all of them to reach four services: GitHub, Slack, a Postgres database and your notes service. Each app describes tools in its own format, so you write each integration by hand. That is 3 × 4 = **12 integrations**.

Then the notes service adds a field. You update it in three places. Next quarter you add a fourth app, and you owe four more integrations.

## Every integration rebuilds the same three things

Look inside any one of those integrations and you find the same work:

- **Describing the tools.** Names, descriptions and input schemas, written again for each app's format.
- **Moving the messages.** How a call gets from the app to the service and back.
- **Running the code.** Auth, retries and error messages for that service.

None of it depends on which app is asking. "Search the notes" means the same thing to Claude Code as to your harness. The only reason you wrote it three times is that the apps had no shared way to ask.

## Agree on one plug

The Model Context Protocol (MCP), published by Anthropic in November 2024 as an open standard, is that shared way. It has three roles:

- An **MCP server** wraps one service and exposes what it can do.
- An **MCP host** is the AI app. It runs one **MCP client** per server it connects to.
- The client and server talk **JSON-RPC 2.0**, over stdio for a local process or HTTP for a remote one.

A server can offer three kinds of things: **tools** the model can call, **resources** the app can read into context (files, rows, documents), and **prompts**, reusable templates a user can pick. Most servers start with tools.

Discovery and calls are two methods. The host asks:

```json
{ "jsonrpc": "2.0", "id": 1, "method": "tools/list" }
```

The server answers with each tool's `name`, `description` and `inputSchema`, the same three things you wrote in [Function Calling](/c/tools/). The host passes them to the model. When the model asks for a tool, the host sends:

```json
{ "jsonrpc": "2.0", "id": 2, "method": "tools/call",
  "params": { "name": "search_notes", "arguments": { "query": "standup" } } }
```

The result comes back as content blocks, with `isError: true` if the tool failed ([Tool Errors and Recovery](/c/tool_errors/)). The host wraps it in a `tool_result` and the loop carries on.

## Let us check the math

Integrations scale differently. So do the tokens.

<Callout type="math" label="Let us check the math">
**Integrations.** Custom: apps × services = 3 × 4 = **12**. MCP: apps + services = 3 + 4 = **7**. At 5 apps and 20 services: 100 vs 25.<br />
**Tokens.** Connect 4 servers with 15 tools each at about 300 tokens per definition: 4 × 15 × 300 = **18,000 tokens** on every model call.<br />
A 20-turn session resends them 20 times: 360,000 tokens. At medium sim prices ($3 per million input, illustrative) that is **$1.08 per session** on tool definitions alone, before the task itself.
</Callout>

MCP makes it cheap to connect a server. It does nothing to make the connected tools cheap to carry.

## The tradeoff: easy to plug in, easy to plug in too much

A standard plug means you can connect a new server in one line of config. That convenience has costs:

- **Context bloat.** Every connected tool rides on every call, and look-alike tools from different servers confuse the model ([Designing Good Tools](/c/tool_design/)). Connect only the servers a task needs, cache the stable prefix ([Prompt Caching](/c/caching/)), and load tools on demand when the host supports it.
- **Untrusted descriptions.** A server's tool descriptions and results go straight into the model's context. A malicious or compromised server can use them to steer the agent ([Prompt Injection](/c/prompt_injection/)).
- **Someone else's code with your keys.** A local server runs with your credentials. Review servers like any dependency, and gate risky tools ([Permissions and Sandboxing](/c/permissions/)).

## In the real world

Claude Code and Claude Desktop are MCP hosts. You register a server, such as a GitHub, Postgres or filesystem server, and its tools appear next to the built-in ones. The model calls them like any other tool; the host routes each call to the right server. In the code lab you build a tiny notes server with `tools/list` and `tools/call`, connect a client, and hand its tools to the agent loop.
