## Your team asked for an agent. You opened the editor first.

Your team gets 400 new GitHub issues a day and wants an agent to triage them: find duplicates, read the issue, add a label. You wire up the largest model, give it every tool the GitHub API has, and run it on a sample. The labels look good. Then you read the bill: $0.42 per issue, $170 a day, against a budget of $40. And on issue #4815 it closed a real bug as a duplicate.

Nothing in that design was wrong in isolation. You just skipped the questions that would have ruled it out before you wrote any code.

## Agents fail where nobody asked the question

Most agent failures are not model failures. They are design questions nobody answered: how much can one task cost, what is the agent never allowed to do, when does it stop, how do you know it works. Each unanswered question becomes a default, and the defaults are bad: the biggest model, every tool, no cap, no evals.

So answer them in a fixed order. Each step uses the answers from the one before.

## The six steps

**1. Scope the job and the failure cost.** Write the job in one sentence, then ask what one wrong action costs. A wrong label costs a maintainer ten seconds. A wrongly closed bug costs a user's trust. If a plain script or a single prompt does the job, stop here ([When Not to Build an Agent](/c/when_not/)).

**2. Napkin math.** Tasks per day × turns per task × tokens per turn × price. This gives you dollars per task, and it picks the model tier for you ([Cost and Latency Math](/c/cost/)).

**3. Tools and permissions.** List the smallest set of tools that does the job. Mark each one allow, ask or deny, based on the failure cost from step 1 ([Permissions and Sandboxing](/c/permissions/)).

**4. Loop and context strategy.** How many turns is normal, what is the cap, and what happens when the context fills ([Stop Conditions and Budgets](/c/stop_conditions/), [Context Management](/c/context_mgmt/)).

**5. Evals and guardrails.** Write 20 to 50 test tasks with known answers before you tune anything, and decide which outputs get checked ([Why Evals Come First](/c/evals/), [Guardrails](/c/guardrails/)).

**6. Tradeoffs, then build.** Write down what you gave up and why. Then build the smallest version and run the evals.

## Let us check the math

Back to the triage agent. A typical issue takes 5 turns: read, search, maybe read a duplicate, label, answer. The context starts at 2.5k tokens (system prompt, tool schemas, the issue number) and each turn adds about 1.2k (issue text, search results).

<Callout type="math" label="Let us check the math">
Input per turn: 2.5k, 3.7k, 4.9k, 6.1k, 7.3k. Total: **24.5k input tokens**. Output: 5 × 150 = 750 tokens.<br />
**Large** ($15/$75 per million): 24,500 × $15/M + 750 × $75/M ≈ $0.37 + $0.06 = **$0.42 per issue**, $170 a day.<br />
**Medium** ($3/$15): $0.074 + $0.011 = **$0.085 per issue**, $34 a day.<br />
**Small** ($1/$5): $0.025 + $0.004 = **$0.03 per issue**, $11 a day, but it mislabels more.<br />
Budget: $40 / 400 = **$0.10 per issue**. Medium fits with 15% headroom. Large is out before you write a line of code.
</Callout>

Prices are this course's illustrative sim prices. The shape is what matters: the budget per task decides the tier, and the tier decides how much reasoning you can buy per turn.

Now the other steps fall out. Step 1 said a wrong closure is expensive and a wrong label is cheap, so step 3 denies `close_issue` and allows `add_label`. Step 4 notices that vague issues ("how do i do the thing") tempt the model into re-running the same search, so it caps the loop at 12 turns. Step 5 builds 40 past issues with the labels your maintainers actually chose.

## The tradeoff: the method costs you a day up front

Writing six answers before building feels slow, and some answers will be wrong. Three ways to keep it cheap:

- **Timebox it.** One page, one hour. The goal is to rule out bad designs, not to predict everything.
- **Let evals correct the math.** Your turn and token estimates are guesses. Run 20 eval tasks, read the real numbers from your traces ([Tracing and Observability](/c/tracing/)), and redo step 2.
- **Start with less autonomy.** When you are unsure about a failure cost, choose ask over allow. You can loosen a permission after a week of clean traces; you cannot undo a closed issue.

In the lab you get the draft triage agent from the problem above. Apply steps 2, 3 and 4 to it. Then the next four lessons walk the same method through a coding agent, a support agent, a research agent and a browser agent.
