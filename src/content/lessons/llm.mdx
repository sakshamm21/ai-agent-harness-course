## You asked for three sources. Two of them do not exist.

You ask a chat model for three papers that support a claim. It gives you three titles, authors, years and journals, formatted perfectly. You search for them. Two of the three were never written.

<Trace caption="Three perfectly formatted citations, and only one of them points at a real paper." steps={[
  { role: "user", text: "Give me three papers that support this claim." },
  { role: "model", text: "Three titles, with authors, years and journals, neatly formatted.", tag: "end_turn" },
  { role: "result", text: "Paper 1: found.", good: true },
  { role: "error", text: "Papers 2 and 3: no such paper was ever written.", bad: true },
]} />

This is not rare and it is not a glitch. In 2023 lawyers in a New York case, Mata v. Avianca, filed a brief that cited six court decisions that did not exist. A chatbot had written them, and the judge sanctioned the lawyers. To see why it happens, and why it will keep happening unless you design for it, you need to know what the model is actually doing.

## It is autocomplete, run one token at a time

A large language model (LLM) does one thing. It reads a sequence of **tokens**, which are words or pieces of words, and gives every possible next token a probability. Then one token is picked, added to the end, and the whole thing runs again.

After "The capital of France is", the token " Paris" might get 0.96. After "A good paper on this is", there is no single right answer, so the probability spreads across thousands of plausible author names and titles. The model picks one, then the next, then the next. Each choice is locally reasonable. Nothing in the process checks that the finished citation points at a real paper.

<Compare caption="The model scores plausible next tokens; nothing checks that the result is true." cols={[

That is the key idea of this whole course: the model produces **plausible text**. It is very good plausible text, often correct, because the training data is full of correct facts. But "plausible" and "true" only overlap where the model saw enough evidence.

## Generation is a loop: score, sample, append

Here is the whole process. You will build a toy version of it in the code lab.

<Flow steps={["Tokens so far", { label: "Model", sub: "scores every next token", kind: "hl" }, { label: "Sample", sub: "temperature reshapes odds" }, "Append token"]} loop loopLabel="repeat until a stop token or max_tokens" caption="Every answer, however long, is written one token at a time." />

Two settings control the "sample" step:

- **Temperature.** At 0, the model always takes the top token, so the same prompt gives the same text. At 1, it samples from the probabilities as they are. Above 1, unlikely tokens get boosted and the text gets stranger.
- **max_tokens.** A hard cap on how many tokens it writes. Hit it and the answer stops mid-sentence.

Because each token depends on the ones before it, an early odd pick sends the rest of the answer down a different path. That is why the same question can get two different answers.

It also explains **streaming**. The model does not have the answer and then send it. It writes it piece by piece, so an API can send you each piece as it is made.

## Let us check the math

Use the toy model from the code lab. After "The", the next-token probabilities are cat 0.5, dog 0.3, model 0.2.

<Callout type="math" label="Let us check the math">
**Temperature 0.5** raises each probability to the power 1/0.5 = 2, then rescales so they sum to 1.<br />
0.5² = 0.25, 0.3² = 0.09, 0.2² = 0.04. Total = 0.38.<br />
New odds: cat 0.25/0.38 = **0.66**, dog 0.09/0.38 = **0.24**, model 0.04/0.38 = **0.11**.<br />
Lower temperature made the favourite more likely (0.5 to 0.66).

**One whole sentence** at temperature 1: "The cat sat ." has probability 0.7 (The) × 0.5 (cat) × 0.6 (sat) × 1.0 (.) = **0.21**. Run it 100 times and you get that exact sentence about 21 times. The other 79 are different.

**Time.** If a model writes about 50 tokens per second, a 400-token answer takes 400 / 50 = **8 seconds** to finish. Streaming shows the first words in well under a second instead of a blank screen for 8.
</Callout>

## The tradeoff: low temperature buys repeatability, not truth

Setting temperature to 0 makes the output more repeatable. It does not make it more correct. A greedy model invents a citation just as fluently; it simply invents the same one every time. And you lose variety you sometimes want, like several draft subject lines to pick from.

<Compare caption="Temperature 0 makes the answer repeat; only facts or a lookup make it true." cols={[
  { title: "Temperature 0", sub: "same pick every time", kind: "bad", rows: ["+ Repeatable output", "- Invents the same citation each run", "- Loses variety you sometimes want"] },
  { title: "Give it the facts", sub: "source in the prompt", kind: "good", rows: ["+ Quotes text in its context", "+ Far more reliable than recall"] },
  { title: "Let it check", sub: "a search tool", kind: "good", rows: ["+ Looks the paper up", "+ No guessing at titles"] },
]} verdict="Repeatable is not the same as correct." />

The real fixes change what the model is predicting from:

- **Give it the facts.** Put the source document in the prompt, or let it search. A model quoting text in its context is far more reliable than one recalling from training. See [Retrieval-Augmented Generation](/c/rag/).
- **Let it check.** A model with [tools](/c/tools/) can look a paper up instead of guessing its title.
- **Constrain the shape.** When code reads the answer, ask for [structured output](/c/structured/) and validate it. For runs that must repeat exactly, see [Taming Nondeterminism](/c/determinism/).

## In the real world

The Claude API exposes this loop directly. You set `temperature` (0 to 1) and `max_tokens` on each request, and when you ask for a stream you receive the answer as a series of small text deltas. If the response ends with `stop_reason: "max_tokens"`, the loop hit your cap before the model chose to stop. Every agent in this course is built on calls like this one.

```python
with client.messages.stream(
    model=MODEL, max_tokens=400, temperature=0,
    messages=[{"role": "user", "content": "Name three papers on this claim."}],
) as stream:
    for text in stream.text_stream:   # small deltas, as they are made
        print(text, end="", flush=True)
    final = stream.get_final_message()

if final.stop_reason == "max_tokens":
    print("\n[cut off: hit the 400-token cap]")
```
