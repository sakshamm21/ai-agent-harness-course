## The plan said "run the codemod." The codemod failed. It ran it again.

Your coding agent has to upgrade three services from payments SDK v2 to v3. It starts well, with a plan: read the changelog, run the official codemod, run the tests, report. Then the codemod exits with "Unsupported pattern: custom wrapper PaymentsClient. 0 files changed."

The agent runs the codemod again. Then it runs the tests, which fail with "sdk.charge is not a function". Then it reports: "Plan complete. Upgrade done." In the lab, only about 3 upgrades in 10 actually finish.

## A plan written once becomes a script

Writing a plan first is good. It makes the model think about the whole task before it touches anything, and it gives you something to review. The problem is what happens next.

The plan lives in one early message. It has no status, no way to mark a step failed, and no way to add a step. So the agent treats it as a script. When step 2 fails, its options are to repeat step 2, move on to step 3 as if step 2 worked, or give up. None of those is "the codemod cannot handle this repo, so edit the six call sites by hand."

On long tasks it gets worse. The plan scrolls further up the context with every tool result, and the model sees less of it each turn.

## Keep the plan as state the agent can rewrite

Give the agent a todo list it owns, and a tool to change it. Each item has a status. After every step, and always after a failure, the agent rewrites the list.

```python
@tool
def update_todos(items: list[dict]) -> str:
    """Rewrites the task list. Each item: {text, status}, where status is
    pending, in_progress, done or failed. Use it after each step, and
    whenever a step fails or you learn something that changes the plan."""
    STATE["todos"] = items
    return render(items)   # "[x] read changelog\n[!] codemod failed ..."
```

A failed step produces new steps." />

Now the failure has somewhere to go. After the codemod error, the agent writes:

```text
[x] read the v3 changelog
[!] run_codemod: no support for our PaymentsClient wrapper
[ ] edit the 6 call sites by hand: charge() -> payments.create()
[ ] run_tests
```

Two things help here. The failed step stays visible, so the agent does not retry it. And each rewrite puts a fresh copy of the goal and progress at the end of the context, where the model pays the most attention. You can also show the list to the user, who sees what the agent thinks it is doing.

## Let us check the math

Say a 5-step plan, and each step has a 10% chance that reality disagrees: a tool fails, a file is not where the plan expected, a test reveals something new. Sim prices (illustrative), medium tier at $15 per million output tokens.

<Callout type="math" label="Let us check the math">
**Plan survives untouched:** 0.9⁵ = **0.59**. So 41% of tasks need a change.<br /><br />
**Fixed plan:** assume it rarely recovers, say 1 time in 5. Success ≈ 0.59 + 0.41 × 0.2 ≈ **0.67**.<br />
**Replanning:** assume it recovers 9 times in 10. Success ≈ 0.59 + 0.41 × 0.9 ≈ **0.96**.<br /><br />
**Cost of the list:** about 5 updates of 250 output tokens each = 1,250 tokens.<br />
1,250 × $15/M ≈ **$0.019 per task**, plus a few hundred more input tokens per turn.<br />
Each update is also a turn: about 1 to 2 extra seconds each.
</Callout>

<Bars caption="Replanning recovers most of the 41% of tasks where the plan meets reality." unit="%" max={100} bars={[
  { label: "Plan survives as is", value: 59, note: "59% · 0.9⁵" },
  { label: "Fixed plan", value: 67, kind: "bad", note: "≈ 67%" },
  { label: "Replanning", value: 96, kind: "good", note: "≈ 96% · +$0.019" },
]} />

Two cents and a few seconds to turn a third of your failures into successes. The lab task is harsher: the codemod fails every time, so without replanning almost every run goes wrong.

## The tradeoff: plans cost turns, and agents can replan forever

A todo list is not free, and too much planning is its own failure:

<States caption="A replan should lead back to action; a turn or cost cap stops a loop of rewrites." states={[

  { id: "done", label: "Done", sub: "every item done", kind: "good" }, { id: "stop", label: "Stopped", sub: "turn or cost cap", kind: "bad" },
]} edges={[
  { from: "act", to: "update", label: "observe" }, { from: "update", to: "act", label: "next item" },
  { from: "update", to: "done", label: "all done" }, { from: "update", to: "stop", label: "budget hit" },
]} path={["act", "update", "act", "update", "done"]} />

- **Overhead on easy tasks.** A one-step question does not need a five-item plan. Let the agent skip the list for short tasks, and use it when a task has three or more steps.
- **Endless replanning.** An agent that rewrites its plan every turn without acting is stuck, just more politely. Cap the turns and cost ([Stop Conditions and Budgets](/c/stop_conditions/)), and count replans in your traces ([Tracing and Observability](/c/tracing/)).
- **Plans that drift from the goal.** Each rewrite can quietly drop a requirement. Keep the original task fixed at the top and check the final result against it, with tests or a grader ([Evaluator–Optimizer](/c/evaluator_optimizer/)). For risky changes, have a person approve the plan before the agent acts ([Human in the Loop](/c/hitl/)).
