## It found retry code. It was the wrong retry code.

A developer asks your agent: "What is the maximum delay between webhook retries, and where is it set?" The codebase has 2,400 files. A retriever embeds the question and pastes in the 3 most similar chunks. The top hit is `http/client.py`, the HTTP client's exponential backoff for outgoing API calls. The agent answers "30 seconds, line 88". The real cap is 15 minutes, in `webhooks/dispatcher.py`.

In the lab, this setup gets **45%** of codebase questions right. The retriever is working as designed. It returned the most similar code. Similar was the problem.

## Code has names, and similarity ignores them

Embeddings compare meaning and topic. Two retry loops with backoff look almost the same, whatever they retry. What separates them is exact names: `WEBHOOK_MAX_BACKOFF`, `dispatch_with_retry`, `validate_api_key`. Those are precisely what embeddings blur.

Code also breaks the other assumptions of [RAG](/c/rag/):

- **The answer spans files.** The constant is defined in `config/settings.py`, but the dispatcher clamps it with `min(WEBHOOK_MAX_BACKOFF, 900)`. A single search returns one of them.
- **Chunks cut functions.** A fixed-size chunker splits a function from its callers, or its signature from its body ([Chunking](/c/chunking/)).
- **The index goes stale.** Code changes on every commit. An embedding index has to be rebuilt to stay true, and a stale one returns code that no longer exists.

## Give the agent search tools and let it look

**Agentic search** moves retrieval into the [agent loop](/c/agent_loop/). Instead of one search before the model answers, you give the model tools, and it searches the way a developer would.

- `grep` for the exact name or a pattern: `grep -rn "MAX_BACKOFF" src/`
- `read_file` on the hit, to see the code around it
- `grep` again for what it just learned: who calls `dispatch_with_retry`, where the constant is overridden
- answer, citing file and line

Each step uses what the last one found. That is the advantage over one-shot retrieval: the agent can refine its query, follow a reference, and notice when a matching line is not the whole story. In the lab, grep alone gets to 35% (the agent answers from the grep hit without opening the file). Grep plus `read_file` gets **98%**.

There is no index to build. The search runs against the files as they are right now.

## Let us check the math

Using the lab's numbers, at sim prices for a medium model (illustrative):

<Callout type="math" label="Let us check the math">
**RAG:** 2 turns, about **$0.020** per question, 45% correct.<br />
Cost per correct answer: 0.020 / 0.45 ≈ **$0.044**.<br />
**Agentic search:** about 3.5 turns, **$0.035** per question, 98% correct.<br />
Cost per correct answer: 0.035 / 0.98 ≈ **$0.036**.<br />
**Latency:** 3.2 s versus 6.4 s per question, twice as slow.<br />
**The index you skip:** 2,400 files × about 1,500 tokens = 3.6 million tokens to embed, then re-embed the changed files on every commit.
</Callout>

Agentic search costs 75% more per question and is cheaper per right answer, because a wrong answer about code costs a developer far more than three cents.

## The tradeoff: the agent has to know what to look for

Grep is exact, which is both its strength and its weakness.

- **Vocabulary mismatch.** If the user says "login" and the code says `authenticate`, grep finds nothing. Good agents try synonyms and patterns, but on a large prose corpus (support tickets, legal documents) a semantic index still finds candidates grep cannot. Many systems give the agent both: grep plus a `semantic_search` tool.
- **More turns, more tokens.** Each search adds results to the context. Delegate wide searches to a [subagent](/c/subagents/) that returns a short summary, and set [stop conditions](/c/stop_conditions/) so a fruitless search ends.
- **Tool design matters.** Results need paths and line numbers, and caps on output size, or one broad grep floods the window ([Designing Good Tools](/c/tool_design/)).

## In the real world

Claude Code searches a repository with tools (Grep, Glob, Read) in its loop, and does not build an embedding index of your code. Its developers have said publicly that they tried vector-database RAG early on and found agentic search worked better for code. The SWE-agent research project reached a related conclusion: giving the model compact search and file-viewing commands with clear output improved how many real GitHub issues it could fix.
