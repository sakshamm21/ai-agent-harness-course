## The search filled the window. The task fell out of it.

The payments team is retiring `charge_v1`. You ask your coding agent to find every caller, migrate it to `charge_v2`, and keep the tests green. The window is 200k tokens and the conversation so far uses 60k.

The agent greps for `charge_v1` and gets 20k tokens of matches. It opens 40 files to see how each call is built, about 4k tokens each: another 160k. That is 60k + 180k = 240k tokens, 40k more than fits. The oldest messages fall out first, and the oldest message is your task. The agent migrates the callers it can still see and reports "Done". Four callers are never touched.

## The main agent needed the answer, not the search

Look at what those 180k tokens were for. The agent needed one thing from them: a list of call sites and how each one builds `amount` and `card`. Written down, that list is about 2k tokens. The other 178k are grep noise, imports, unrelated functions and test fixtures.

<Compare caption="Of 180k tokens of search output, the main agent needed about 2k." cols={[
  { title: "What came back", sub: "180k tokens", kind: "bad", rows: ["- grep noise and imports", "- Unrelated functions", "- Test fixtures"] },
  { title: "What was needed", sub: "about 2k tokens", kind: "good", rows: ["+ Every charge_v1 call site", "+ How each builds amount and card"] },
]} verdict="Keep the search out of the main transcript and keep only the answer." />

But in a single loop, every tool result goes into the one transcript, and it stays there. The noise from step 2 rides along on every turn after it, pushing out the parts that matter: the task, the plan and the edits. [Compaction](/c/context_mgmt/) can shrink it later, but by then the model has already been working with a crowded window.

## Give the side task its own context

A **subagent** is a second agent loop, started by the main one, with a fresh context. The main agent calls it like a tool, with a brief. The child does the noisy work in its own window, and only its final answer comes back as the tool result.

```python
@tool
def task(brief: str) -> str:
    """Starts a subagent with a fresh context for a self-contained side task.
    Use it for searches and reading many files. Returns only its final report."""
    child = run_loop(
        small_model,
        tools=[grep, read_file],                  # read-only: the child cannot edit
        messages=[{"role": "user", "content": brief}],
        system="Do the task. Reply with a list of file:line and one line on each.",
        max_turns=15,
    )
    return child.final_text                       # ~2k tokens, not 180k
```

Three choices make it work:

- **A real brief.** The child sees nothing of the main conversation. The brief says what to find, where, and what shape the answer should take.
- **A structured result.** Ask for `file:line` plus one line each. A list can be checked; "I found several callers" cannot.
- **Fewer tools, smaller model.** Search does not need `edit_file` or a large model. A read-only child on a small tier is safer and cheaper.

## Let us check the math

Use the sim prices (illustrative): medium $3 and small $1 per million input tokens. Say the search takes 8 turns, and the material it adds averages 90k tokens per turn. Afterwards, the main agent works for 10 more turns.

<Callout type="math" label="Let us check the math">
**All in the main agent (medium tier), counting only the search material:**<br />
Search turns: 8 × 90k = 720k tokens × $3/M = $2.16.<br />
Carrying 180k on each of the next 10 turns: 1.8M tokens × $3/M = $5.40.<br />
Total **$7.56**, and it does not even fit: 240k > 200k.<br /><br />
**With a subagent on the small tier:**<br />
Search turns in the child: 720k tokens × $1/M = $0.72.<br />
Carrying a 2k summary on 10 main turns: 20k × $3/M = $0.06.<br />
Total **$0.78**, and the main context peaks at about 62k.
</Callout>

<Bars caption="Cost of the search material alone: about ten times less with a small-tier subagent." unit="$" bars={[

About ten times cheaper, and the task never leaves the window. The saving comes from two places: the cheaper model, and not paying again and again for noise.

## The tradeoff: a summary is a lossy copy

The main agent now trusts a report it cannot check against the raw output.

  { role: "note", text: "The child listed 7 of 11. The check found the other 4.", good: true },

- **The child can miss things.** If it lists 7 of 11 callers, the main agent migrates 7. Ask for a checkable result, and verify it cheaply: one `grep -c charge_v1` after the edits costs 50 tokens.
- **Delegation has overhead.** Each child pays for its own system prompt and its own first turns, and it adds latency. A 3-file search is faster done directly. Independent children can run at the same time, as in [parallel tool calls](/c/parallel_tools/) and the [orchestrator–workers](/c/orchestrator/) pattern.
- **Context does not flow back in.** The child cannot ask "which service did you mean?". Whatever it needs must be in the brief, the same problem as [handoffs](/c/handoffs/).

## In the real world

Claude Code documents subagents publicly. Each one is a Markdown file with YAML frontmatter, in `.claude/agents/` for a project or `~/.claude/agents/` for you, with a name, a description that tells Claude when to use it, an optional list of tools and an optional model. The docs say each subagent runs in its own context window, and Claude can delegate to one on its own based on the description, or when you ask by name.

```markdown
---
name: caller-finder
description: Finds every call site of a function. Use for searches that read many files.
tools: Grep, Glob, Read
model: haiku
---
Search the codebase for the function in the brief.
Reply with file:line and one line on how each call is built.
```
